# Introduction

WP3 aims to provide guidance, recommendations, technical expertise, and
implementation support expertise to all use case efforts in terms of
data analysis and processing. While the tasks will be executed by the
use case developers, support will be given to assist in all data
handling steps after ingestion and provision on both the Rasdaman- and
EOxHub services as part of FAIRiCUBE's overall data and model services.
Special emphasis is given to the data-driven machine learning (ML) model
generation.

This deliverable needs to be seen as one item of a classical and logical
execution of a machine learning application. Given the
availability/ingestion of data, we first perform an exploratory data
analysis to get familiar with the data, analyse statistical parameters
and distribution, and check for completeness, outliers and other
characteristics which could be relevant to the choice of the machine
learning. This in-depth data analysis is covered by the deliverable
*D3.1 UC exploratory data analysis*.

Subsequently, the raw data might require conversion into features
through a data engineering process. This could imply a combination of
several input data sources or applying simple mathematical operations to
enhance the meaningfulness of the raw data given the relationships that
are to be revealed. The more a priori information is available, the
better the feature engineering process can be performed. Based on the
findings from the exploratory data analysis, the formulation of the
research question, and the relationship between raw data
sources/features, machine learning algorithms can be recommended to
establish a baseline model if this is not provided by use case owners.
Starting from the most efficient machine learning algorithm, more
advanced ML methods can be identified to form a machine learning
strategy. Several different methods might also be tested to recommend a
method based on computational demands and accuracy of the ML output.
Typically, the testing of ML algorithms is performed on a subset of the
original input data or selected cases. The feature engineering process,
testing of ML algorithms and the recommendation of a cascade to ML
algorithms, as well as analysing the output of ML methods is covered by
deliverable *D3.2 Machine learning strategy specific for each use case*.

As the FAIRiCUBE Hub ultimately aims to provide resource estimations and
guidance for ML applications, we want to collect and share computational
parameters, timings, and requirements and give an outlook on the
expected scalability of the ML problems defined by the use cases. For
each ML algorithm identified and executed as described in D3.2 we
collect information on e.g., disk storage, CPU runtime, main memory
consumption, describe the hardware and environment where the ML
algorithm is executed on and list essential libraries that are needed to
exactly replicate the ML application. This technical documentation of
the ML execution is covered in this deliverable *D3.3 Processing and ML
applications.* Chapter 2 covers the technical description of how we
measure, monitor and report the resource estimates while chapter 3 shows
some monitoring examples representative for each FAIRiCUBE use case
(UC). Furthermore, any software or tool development that have surfaced
as part of the UC execution and that can have a wider use for other UCs
or beyond the FAIRiCUBE project are briefly described in chapter 4.

In summary, the exploratory data analysis (D3.1) can be seen as
essential input to the development of a UC-specific machine learning
strategy (D3.2) whereas the technical description in D3.3 (this
document) acts as a reference to follow up on the execution and serves
as valuable input to estimate the demands for other ML applications.

# Processing and ML applications 

Monitoring computational resources can provide three significant
advantages. Firstly, it allows us to provide insights and estimations to
other users who may be running similar jobs on similar hardware. This
information can serve as a starting point to scale it for different
hardware configurations. This will help the project planning of
especially computational heavy tasks. Usually, regular processing and
several basic machine learning methods scale linearly.

Secondly, information on hardware requirements and resource usage can
directly translate into costs of cloud resources which is also
frequently unknown during the project planning. Finally, collecting
information on the actual performance and demands of computational tasks
can be the starting point for numerical optimization especially when
expectations are not met by the measures. Optimization can of course
include the careful balance of computational efforts/needs with the
output metrics as well. Not in all cases the optimal solution is the
most accurate one but a well-selected compromise of resources and
sufficient accuracy.

## Monitoring methods 

Monitoring of computational resources and demands have long been driven
by limitations of the availability of local computational resources.
Nowadays, there seems to be no limit concerning the availability but
more on the financial aspect of securing \[cloud\] resources and the
environmental implications of executing computational jobs. In the
following, we have listed the parameters and measurement methods for
those parameters that we considered useful to estimate costs and also
prepare environmental impact assessments as a result of the energy
consumption. The monitoring methods focus on the execution on local
(e.g. laptop or workstation pc) or cloud (e.g. cluster pc, virtual
machines) hardware where direct access to built-in monitoring tools is
available (see chapter 0) or where we can execute automatic resource
monitoring scripts (see chapter 2.1.2). Note that we mostly focus on the
dominant data science programming languages Python and the operation
system Linux first and do not cover all variants of Use Case work (e.g.
R, Java or JavaScript). The automatic monitoring concept in chapter
2.1.2 can however ported to other scripting languages and platforms
easily.

We then compared the results and concluded that none of the methods can
currently be considered 100% reliable for the following reasons:

-   manual measurements, by their very nature, cannot be considered
    extremely accurate. This is because some of the needed metrics
    cannot be calculated, while others only allow the output to be
    calculated visually, without having precise control over the running
    processes and what is happening inside the machine.

-   more iterations would have been required to fine-tune the automated
    process.

Given installation status on a local computer/server resource,
monitoring can be obtained by a user directly. For monitoring on EOX
Hub, a user account is required. Firstly, a GitHub account needs to be
set up with access to the FAIRiCUBE project. Secondly, the GitHub handle
needs to be configured and assigned to a use case specific EOX Hub
server option. This is currently a manual process which can be executed
by any member of the FAIRiCUBE GitHub organisation. Finally, a user can
connect to <https://eoxhub.fairicube.eu> using its GitHub credentials.
Once connected, the user can create, run, and share Jupyter notebooks
using **AWS (**Amazon Web Services) **resources** configured by EOxHub.
Similar to local compute infrastructure, basic resource monitoring can
be performed in the FAIRiCUBE EOX Hub as well.

### Automatic

To automate resource monitoring, a tool called 'Measurer' has been
developed and tested that can collect information about the
computational resources used and the characteristics of the executing
machine at the end of the execution of an a/p resource. The information
is stored in a csv file that can be uploaded through the metadata form
during the a/p resource metadata editing/input process. As more than one
csv file can be generated for each a/p resource (depending on the
execution configuration), multiple csv files may be loaded.

The Measurer is a Python library that can be simply called from any
Python source code to compute parameter values. It is worth noting here
that our library works only on Python scripts. More details together
with source code and examples of use can be found in the related folder
[^1] of the GitHub common-code[^2] repository. The Table 2 below shows
the resource consumption metrics and how they are calculated by the
Measurer.

Obviously, according to the current results, the automatic computation
of resources requires further tuning to be considered as the main tool
for documenting the computational resources. For instance, at this
level, 'total consumed memory on machine' computes what a program
allocates between two lines of code. However, a program requires more
than only the memory used by a few lines of code (e.g., importing
libraries, etc). For example, we have noticed that running the regressor
requires more than 520 MB according to the task manager but only 14 MB
was reported (see Table 3).

Also, the measurer library fails to return the exact frequency of the
processor when a program is run on a server (e.g., on AWS configured by
EOxHub). From Table 3, we notice that 'Available on machine' is almost
doubled compared to the manual reporting. This is because, even though
we allocate a memory of only 32GB from AWS, some more resources are
allocated to us randomly when free.

Overall, the measurer library is a relevant initiative to automatize the
documentation of computational resources. It has matured enough to be
included as a reference monitoring tool for each processing job to
automatically. As a result, as for now, we consider manual reporting for
the rest of the report.

## UC1 Urban adaptation to climate change

The UC1 team shares an AWS S3 bucket in the EOXHub to ingest, process
and share data. We have used the currently configured EOXHub profile
(c5.4xlarge CPU) with an AWS resource of 7 GB of RAM and 1.8 GHz CPU. We
have implemented ML algorithms in Jupyter notebooks and Python scripts.

For the **European level application** (EU cities clustering exercise)
the ML algorithms were not memory or time consuming, we did not have any
problem running them within the currently configured EOXHub profile. The
clustering itself was implemented using the Python library
*scikit-learn,* and the library *seaborn* was used for results
visualization. The pre-processed city data cube was stored in the S3
bucket in CSV format, and the I/O was handled with the Python data
analysis library *pandas*. The data size is less than 110 KB (1,000 rows
and 6 columns). Generating the city data cube from the original gridded
was the most time-consuming part.

Table 5 provides an overview of the resource usage for each main
process, starting from the calculation of features to the execution of
ML algorithms. We can clearly see that the process that consumed
resources the most is "Calculating level 1 land classification ratios"
(e.g., more than 900 MB of memory usage and more than 2 hours). This is
because it requires uploading and processing data from different cities.
On the other hand, running the clustering algorithms required between 1
and 10 MB only. Calculating level 1 land classification ratios was very
time-consuming (more than 2 hours). However, we can clearly see that the
overall ML process was fast (around 10 seconds), with clustering
algorithms running in less than 1 second, except Mean-Shift that
required more than 7 seconds. In addition, running Bidirectional LSTM
and Gradient boosting regressor for gap filling was very fast, however
with a relatively high memory usage, 968 MB and 520, MB respectively.
Cost-wise, in addition to the AWS fixed daily deduction of around 3\$,
calculating level 1 land classification ratios and the clustering
processes, for example, cost between 20\$ and 25\$ each for computing
(i.e., using AWS resources).

For the **local level application** (invasive plant species distribution
in urban context), we have used the species distribution model Maxent as
implemented in the Python library *elapid* with default parameters. In
addition, we have used the [SHAP (SHapley Additive
exPlanations)](https://shap.readthedocs.io/en/latest/example_notebooks/overviews/An%20introduction%20to%20explainable%20AI%20with%20Shapley%20values.html)
approach (and Python implementation) to explain and identify the most
important features used for learning the species distribution. The model
with explanatory analysis has consumed around 1.5 GB of memory and run
in almost 45 minutes (with 1'000 samples for the SHAP analysis). The
most time-consuming process by far is the explanatory analysis.

**Causal machine learning**

In the Causal Machine Learning (CML) task of the use case we explored
the use of Causal Graph Analysis, to proof the expected causal
correlations between agricultural activities and biodiversity, expressed
as species richness related to selected farmland bird species. This
biodiversity indicator is derived from the SDM results described in the
previous step. For the farming activities we used proxy data, such as
the crop rotation index and the grassland mowing intensity. The
following performance and resource usage measurements are from an
experiment using the data from the arable zone of our study region
(farmland birds species richness, the crop rotation index, and various
environmental covariates and confounding variables).

Briefly, there are three steps in causal graph analysis: (i) Deriving an
*estimand* from a graph of the expected correlations. This estimand is
the causal quantity we want to know about, e.g., "what is the average
increase in farmland bird species richness if the crop rotation index is
increased by one unit?"; (ii) Computation of the *estimate*\--the
numerical approximation of the estimand, derived from the input data;
(iii) *Refutal* of the estimate by checking if the result holds up under
possible violations, such as a placebo test, the adding of random
confounders, or a data subset test. When such refutal fails, i.e. the
estimate holds up, it is considered *robust.* Of these steps, the later
in general is the most resource intensive. The following tables show the
resource usage as reported by the Measurer for the three steps mentioned
before. All data was read from an AWS S3 bucket.

## UC5 Validation of Phytosociological Methods through Occurrence Cubes

UC5 integrates vegetation occurrence data with EO data to investigate
and predict species distribution patterns in relation to the EUNIS
Habitat classification system, as illustrated in Deliverables 2.2 and
3.2.

The workflow was first developed for a specific case study using the
European Habitat S22 and its eight characteristic species. All
processing was conducted in R, with datasets and outputs stored both
locally and in the AWS S3 bucket within the EOXHub Lab. Table 16
provides an overview of the computational resources required for UC5.

Downloading and processing occurrence data from GBIF was a relatively
lightweight computational task. In general, the processing time can vary
depending on the number of occurrences requested, and for this case
study, downloading and processing data for eight species took
approximately 3 hours. Despite the large spatial and temporal extent of
the datasets---totalling over 180,000 occurrence points---the memory
requirements remained modest. The raw dataset had an initial size of
32.3 MB, which was reduced to 28.3 MB after data cleaning.

Since GBIF is an open-access resource, no costs were incurred during
data acquisition. Additionally, occurrence data were transformed into a
gridded format, a step that required minimal memory and processing time.

In contrast to occurrence data, processing environmental datasets was
significantly more resource intensive. The datasets, stored in TIFF
format, had a total size of approximately 441 MB, with intermediate data
volumes remaining the same. However, memory consumption during data
extraction and transformation reached approximately 150 GB. The main
processing steps included extracting environmental variables at species
occurrence points and transforming resolution to match modelling
requirements. These operations were computationally demanding due to the
high resolution and extensive coverage of EO data. The total compute
wall time for processing environmental datasets was approximately 2
hours.

The most computationally intensive phase of UC5 was the modelling and
prediction stage, which involved training multiple individual models,
generating predictions, and evaluating results using TSS-weighted scores
in a final ensemble model. The full modelling process had a compute wall
time ranging from 4 to 10 hours, depending on the number of occurrence
data for the species included. Memory consumption during this phase
remained high, reaching up to 150 GB, particularly during model training
and final prediction generation. The ensemble approach, while improving
predictive accuracy, significantly increased computational costs due to
the multiple iterations required.

## QueryCube

As part of UC3 workflow we developed a Python-based tool called
"QueryCube" which allows users to dynamically access and interact with
gridded data stored on the FAIRiCUBE Rasdaman instance. By utilizing the
OGC Web Coverage Service (WCS), this tool enables seamless data
retrieval and interaction, providing users with the flexibility to
specify both spatial locations and the relevant resources for which they
wish to obtain data. Users can input custom coordinates (Latitude,
Longitude, Datetime) in the form of a csv file, with each coordinate
combination carrying a specific ID and specify which layer available in
the Rasdaman OGC Web Services to query. By querying the data with given
coordinates, corresponding data values are retrieved and given back to
the user, creating another tabular file carrying information for
specified parameters. This approach eliminates the need for manual data
extraction from downloaded layers or predefined areas, enabling a broad
range of use cases to retrieve data directly by specifying point
coordinates.

The tool exists as Python code and is accessible via the UC3 GitHub
repository, in which the primary workflow was implemented through
several custom defined python functions, which can either be executed
manually or run as [standalone python
script](https://github.com/FAIRiCUBE/uc3-drosophola-genetics/tree/main/projects/QueryCube)[^10].
Dependencies are documented and can be created by installing the
creating a specific Conda environment as provided in the repository.
Additional functionalities, like accounting for missing data like
approximating Datetime of queries, are available in this software.
Another instance of our tool is a [Web
Application](https://querycube.nilu.no/)[^11] hosted by NILU. Both
implementations rely on the OGC WCS service provided by rasdaman[^12],
with the FAIRiCUBE-specific WCS access[^13] and FAIRiCUBE credentials
for Rasdaman services.

## WCS/WCPS Python libraries

To facilitate easier interaction with the rasdaman WCS/WCPS services for
Python developers, the rasdaman team developed two open-source Python
libraries. The WCS python library ([GitHub
repository](https://github.com/rasdaman/wcs-python-client),
[documentation](https://rasdaman.github.io/wcs-python-client/)) allows
extracting information about datacubes, such as a list of available
datacubes, their bounding box/axes, range type, metadata, etc.
Downloading data is not directly supported, as this is already possible
with the WCPS library. The WCPS python library ([GitHub
repo](https://github.com/rasdaman/wcps-python-client),
[documentation](https://rasdaman.github.io/wcps-python-client/)) allows
to dynamically build WCPS queries and execute on a WCPS server. A query
usually selects a subset of the data and applies some processing,
aggregation and general analytics on its, and finally downloads the
results in a suitable format such as JSON, PNG, TIFF, JPEG, NetCDF, etc.
The documentation provides many
[examples](https://rasdaman.github.io/wcps-python-client/README.html#examples)
of the capabilities.

The implementation of these libraries was prompted by the observation
that use cases (e.g. UC2 and UC3) needed to do a significant amount of
implementation work such as parsing XML to access information about the
available datacubes and send queries on them, which is completely
unrelated to the goals of the use case itself. Hence, hiding these
details behind convenient libraries that a use case can install and use
is valuable and worth as soon as there is more than one use case
accessing WCS/WCPS services from Python code.

## Rasdaman UDF developments

While rasdaman provides an excellent environment for storing and
handling multi-dimensional array data, supporting arithmetic
computation, with spatio-temporal awareness, it has no specific support
for machine learning at this moment. Neither for using ML models for
inference nor for ML algorithms to train models on available data.
Rasdaman however is extensible through the addition of User-Defined
Functions (UDFs), which can be integrated into the core rasdaman server
(see Figure 8) and thus operate directly on the data stored in the data
cubes. Such *data locality* can result in performance benefits, which
are always welcome in the usual time-consuming and compute-demanding
machine learning. Particularly when applying deep learning (DL) models
on complex multi-dimensional and large datasets.

Rasdaman supports the use of UDFs at two different levels (see Figure
8). The closest one to the server (*rasserver*) uses C++ or Python as
programming language and works on the core data cubes that have no
specific notion of spatio-temporal data dimensions. Those are only
available at a higher layer that provides rasdaman's spatial
capabilities. At this level, the UDFs use the Java programming language,
and it is where *Web Coverage Processing Service* (WCPS) requests are
processed first in rasdaman.

Since deep learning models are frequently used for processing Earth
Observation (satellite) data, it seems particularly relevant to add DL
capabilities to rasdaman, with the (reasonable) expectation that it will
be needed to realize the use case. The known main applications of DL in
EO are (1) image classification, (2) image (pixel) segmentation, (3)
object detection, and (4) image generation (new types of applications
are sure to be added in future).

To implement a first proof-of-concept of DL integration into rasdaman we
selected work on image segmentation, which can be used for many purposes
and could be based on an available convolutional neural network (CNN)
model developed and trained in another project for the classification of
Dutch crop types using Sentinel-2 data as input. This model has been
developed using the Python PyTorch framework.

Initially, the core rasdaman server had no direct support for Python UDF
code. Hence a bridge needed to be established between these two worlds
of C++ and Python, which has been achieved by (1) the use of standard
PyTorch functionality to 'trace' the existing model into TorchScript
format (which has no Python dependencies), and (2) writing a rasdaman
UDF in C++ using the libtorch implementation of PyTorch to load and run
the TorchScript model (see Figure 9). All code and further information
are published as part of the FAIRiCUBE project on
[GitHub](https://github.com/FAIRiCUBE/uc2-agriculture-biodiversity-nexus/tree/main/rasdaman-ml-udf)[^14].

This approach allows using a pretrained model for *inference* on data in
data cubes. Since the UDF has been added at the core level, a further
bridging UDF (in Java) was necessary so that WCPS requests can be used
to start model inference and return the results as a geo-referenced data
cube.

The UDF-based DL solution described before has been deployed on a
Virtual Machine (VM) provided by rasdaman for use by the use cases. Some
initial testing on this configuration has been performed, showing that
the solution works and can produce the same model inference results as
the original model when run on a local computer. An example of the WCPS
query with which the model can be invoked is given in Figure 10.

Subsequently, rasdaman developed support for natively writing UDFs in
Python code. Parameter passing between the rasdaman engine and the
Python UDF is made as convenient as possible through intelligent
transparent conversion: numerical and string values are passed as native
Python types, while array values are passed as NumPy arrays in the
Python code. This allows for a much easier integration with the
Python-oriented machine learning community and prevalent ML frameworks
such as TensorFlow, PyTorch, NumPy, and SciKit-Learn. As an example, the
previously discussed C++ UDF was reimplemented as a much simpler Python
UDF (code available on
[GitHub](https://github.com/FAIRiCUBE/uc2-agriculture-biodiversity-nexus/tree/main/rasdaman-ml-udf/proof_of_concept/rasql_python_udf)).

As of now, the UDF concept is mostly suited for the inference of
pre-trained models and therefore relies on the training of ML models on
other infrastructure and the compatibility of these models. Especially
when transferring an ML model from a GPU infrastructure to a CPU
environment, this interoperability might not be guaranteed if it is
actually possible at all. For less demanding ML methods a similar Python
environment can be constructed on both the training and inference
infrastructure to allow for transferability of models.

Furthermore, the ML models that can be deployed as UDF only reflect the
training aspect given the feature input data and the objective of the ML
training. To make ML models available for wider applications, concepts
like transfer learning and adaptation of parts of the model architecture
in the last neuron-layer(s) is required and can currently only be
applied outside of the rasdaman environment. In short, ML models
deployed as UDF modules can and shall only be used for sufficiently
similar format and dimensionality of data and ML-objective as they have
been trained for, which restricts the wide-ranged reuse of the models (a
typical concern for ML models). The most immediate issue is however
posed by the operationalisation of ML models from training to inference
infrastructures.

### Knowledge Base ChatBot

The FAIRiCUBE chatbot [^15]is an intelligent assistant that acts as a
guide to FAIRiCUBE resources. It is a useful tool for those wishing to
interact with the project, thanks to its ability to provide contextually
relevant answers, coupled with a strong retrieval mechanism. The chatbot
support users to find, navigate and understand the FAIRiCUBE Digital
Library[^16] and GitHub artefacts through a friendly interface
illustrated in Figure 14.

![A screenshot of a chatbot AI-generated content may be
incorrect.](media/image17.png){width="6.29166447944007in"
height="3.5416666666666665in"}

[]{#_Ref193701473 .anchor}Figure 14 : Screenshot of the FAIRiCUBE KB
ChatBot

The chatbot application integrates Retrieval-Augmented Generation
(RAG) - a technique that extends the capabilities of generative AI
models by allowing them to retrieve and use information from external
sources - with state-of-the-art technology to ensure that answers are
accurate, context-sensitive and reliable.

Specifically, the integration of retrieval-based search and generative
AI allows the chatbot to seamlessly explore and work with both
structured and unstructured information. The chatbot\'s RAG-based
architecture integrates three key components - OpenAI\'s
text-embedding-3-large model, chromaDB and GPT-4o - into a unified
system. This combination enables the chatbot to provide real-time access
to relevant information, while augmenting it with natural language
generation capabilities. The use of chromaDB for information retrieval
ensures that the system is scalable as new data is incorporated,
allowing it to adapt to changes and enrich the FAIRiCUBE project
information.

When a user submits a query through the interface of the chatbot, the
input is processed by the OpenAI text-embedding-3-large model, which
embeds the query in a high-dimensional vector space. This query vector
is then passed on to ChromaDB, an open-source vector database which is
the chatbot\'s retrieval engine. ChromaDB with pre-computed embeddings
for relevant knowledge base documents identifies the most contextually
appropriate content in the shortest time. The vectors in ChromaDB were
obtained from the GitHub artifacts and all Knowledge Base Digital
Library documents and information using OpenAI\'s text-embedding-3-large
model. The obtained information is combined with the user\'s query and
sent to the large language model, GPT-4o to generate a response
coherent, precise, and similar in tone and structure to human
communication. By anchoring responses in the data provided through
ChromaDB, GPT-4o minimizes the risk of hallucinated or factually
incorrect responses. Combining active information retrieval and
generative reasoning ensures that the chatbot provides answers that are
both conversational and based on real data. More details about the
FAIRiCUBE Chatbot can be found in the ultimate version of Deliverable
D3.4 Processing knowledge base services.

# Summary and conclusion

This deliverable report provides a technical overview of processing and
machine learning applications within FAIRiCUBE, focusing on resource
monitoring, computational requirements, and financial tracking. It
documents methods for monitoring resource usage, including manual and
automatic approaches, and evaluates their effectiveness. Key insights
into financial tracking of AWS resources highlight cost management
strategies for cloud-based ML applications.

The use case analysis covers diverse applications and demonstrates the
computational demands of various (pre)processing steps as well as
machine learning applications, including clustering, species
distribution modeling, causal inference, and deep learning. They also
highlight challenges in balancing accuracy with computational
efficiency.

Additionally, the report presents shared tools and developments that
have originally been developed as part of the specific use case but can
have a wider use outside of the project and thereby contribute to open
science principles. The webservice tool QueryCube can easily provide
geospatial data access for point data locations, the Python libraries
allow for easier WCPS service access, and AI-driven chatbots enhancing
the user interaction with project resources. Several other scripts and
notebooks are provided in a common-code repository that especially cover
transformation and output of geospatial data formats.

Overall, this report provides valuable insights into optimizing ML
applications, resource management, and computational efficiency of data
science work executed on FAIRiCUBE Hub services.
