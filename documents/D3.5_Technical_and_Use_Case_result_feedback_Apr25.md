# Introduction

This deliverable is related to *Task 3.6 Technical and Use Case result
feedback* and will describe the benefits and potentially persistent
drawbacks of executing use case work on FAIRiCUBE Hub services. Thereby
we aim to document and explain what went well, what did not work, and
what new ideas and insights have been developed. This reflects both the
maturity, i.e. readiness level, of FAIRiCUBE Hub service as well as
specific issues of the FAIRiCUBE use case (UC) work. After all, the
divers UC research questions are meant to illustrate what is achievable
given data-availability, appropriate access rights, suitability of the
data science platform for data processing and analysis, as well as meta
data description. These insights will provide meaningful insights in the
shaping of the green deal data space (GDDS).

Note that most of the documentation of the FAIRiCUBE Hub services and
the use case execution is covered by other WP2, WP3 and WP4 deliverables
and shall not be duplicated here. However, together with a brief
introduction and the proper reference to respective deliverable reports,
a realistic assessment is given on the completeness of development of
FAIRiCUBE Hub services and how far the UC work has progressed to allow
for, e.g., upscaling and commercialization. Thereby this report provides
input for further FAIRiCUBE Hub development efforts and exploitation of
use case work.

# FAIRiCUBE Hub feedback

The FAIRiCUBE HUB and its architecture is described in the deliverable
report *D4.1 FAIRiCUBE-Hub-Architecture* and *D4.4
Operational_FAIRiCUBE_HUB* and its validation has been published in
deliverable report *D4_6\_Validation of FAIRiCUBE Hub*. The FAIRiCUBE
Hub[^1] has been deployed, is fully operational and consists of the
FAIRiCUBE Workspaces, a Catalog, the Knowledge Base Services (FAIRiCUBE
Digital Library, Query Tool and Chatbot) and several other services and
apps. The FAIRiCUBE Lab, acting as the central point of user activities,
is based on commercial instances of EOxHub and rasdaman and other
Open-Source components. The EOxHub instance provides a Control Plane, a
JupyterHub providing Jupyter Notebooks, and access APIs to the various
FAIRiCUBE Services (see Figure 1).

In the following, the definitions of the components of the FAIRiCUBE HUB
are listed. Details on the technical and use case feedback addressing
the components follow in the subchapters.

**FAIRiCUBE Catalog:** The integrated catalog providing metadata and
references to ingested datasets, processes, and models available from
FAIRiCUBE.

**FAIRiCUBE HUB:** The overall FAIRiCUBE technical environment
encompassing the FAIRiCUBE Catalog, FAIRiCUBE Services and Applications,
as well as the FAIRiCUBE Lab and the rasdaman workspace.

**FAIRiCUBE Lab - EOxHub Workspace:** A single container for all EOXHub
based workspaces providing the interface to back-ends via various
back-end protocols as well as an execution environment for user provided
workloads.

-   **EOxHub Workspace-Worker Plane:** The user area within the
    FAIRiCUBE Lab where users can collaborate and share the content of
    their workspaces.

-   **EOxHub Workspace-Control Plane:** The administration area within
    the FAIRiCUBE Lab where all configuration and setup is managed

**FAIRiCUBE rasdaman Workspace:** consists of the rasdaman datacube
engine, a multi-parallel distributed database system specialized on the
management and analytics of massive multi-dimensional arrays.

**FAIRiCUBE Services/Apps:** Components providing various ways to access
the data and processing facilities provided by FAIRiCUBE.

**FAIRiCUBE Knowledge Base:** Provides a set of tools to enable
appropriate knowledge of how to apply algorithms and ML techniques to
solve similar demands as those of FAIRiCUBE use cases. It comprises
three core services---a Digital Library for centralized access to
FAIRiCUBE documentation, onboarding materials, machine learning
resources and practical examples, a Query Tool for intuitive
metadata-driven resource discovery, and a Chatbot for real-time
assistance in navigating the KB and accessing relevant resources.

**FAIRiCUBE -- GitHub Repository:** FAIRiCUBE has setup and uses a
GitHub repository very extensively. In this FAIRiCUBE GitHub repository
the catalog data, shared code, use case specific code, as well as the
content of the Knowledge Base and the Community Collaboration Platform
is stored and accessible to FAIRiCUBE users.

The FAIRiCUBE HUB provides a complete working environment where users
can access algorithms and data remotely to obtain computing resources
and tools that they might not otherwise have and avoid the need to
download and manage large volumes of data. This new approach removes the
need to transfer/download large e.g. Earth Observation data sets around
the world, while increasing the analytical power available research
scientists, industry, operational service providers, regional
authorities, and policy analysts. The FAIRiCUBE Hub provides:

-   Easy access to data and the tools to exploit these data.

-   Use of online cloud computing resources which reduces the need to
    download and store large volumes of data locally.

-   Data, visualisation, and processing options that are tailored to the
    needs of science and operational users.

-   Personalised and private accounts that can be accessed from any
    location through the Internet.

-   A clear and intuitive user interface to access the platform
    functionality, including an interactive map portal for visualising
    data and outputs.

-   Access to built-in processors or user-provided processors.

-   Processor outputs that can be used in other processors, shared with
    other users, or download.

-   Access to sufficient processing capacity for analysis of large
    volumes of data.

-   A customisable online development environment with all the necessary
    software tools and libraries to develop processors and optionally
    make them available to other users.

-   A collaboration environment for groups to communicate via a platform
    forum, share software code using the platform code repository, and
    track problems with a built-in issue tracker.

-   Knowledge Base enabling simple access to essential information on
    working with large spatiotemporal datacubes.

## Data catalog

In the early phase of the FAIRiCUBE, it was decided to create a data
catalog based on the SpatioTemporal Asset Catalog (STAC)
specifications[^2]. The STAC browser[^3] using the STAC FastAPI[^4] is
therefore a central element of the FAIRiCUBE data catalog. It is
nevertheless worth noting that the FAIRiCUBE project is not a data
catalog nor data ingestion project and the choice of the data catalog
specification was not based on a careful review of meta data standards
or extensive experience but driven by innovation and curiosity to try
out emerging developments. That implied a risk to use a community driven
specification and implementation that has not matured entirely and this
risk partially materialized. Both the STAC specifications did not
include all relevant metadata fields that FAIRiCUBE has envisioned as
well as some desired features in the STAC browser were missing (i.e. the
free text search).

Further, data ingestion in FAIRiCUBE is triggered due to shortcomings of
data availability, data metadata description and the availability of
APIs. Our project therefore performs data ingestion to bridge gaps while
awaiting the access/development on the data provider side. As a result,
no persistent data access and provisioning is envisioned but the Catalog
is used to demonstrate and test the STAC specification and capabilities,
for example as input to the green deal data space (GDDS). FAIRiCUBE can
thereby serve as technology demonstrator by providing implementation
details, limitations and guidance.

In addition, the data catalog covers the ingestion and provision of two
different infrastructure stacks (rasdaman and EOX workspace) with
different technical implications. The meta data description and the
webservices to request the meta data is the same but splits out into the
ingestion process specific to each infrastructure stack. The validation
of the data ingestion closes the split, and a single data record is
stored as part of the FAIRiCUBE data catalog. On the rasdaman
infrastructure, support for datacube metadata was extended and the
linking with the FAIRiCUBE catalog was provided. As the data catalog is
hosted on the EOX infrastructure hosted as an AWS Kubernetes service,
integration of the data ingested/registered through the EOX
infrastructure was more straight forward. All in all, users are now
enabled to easily find relevant datasets despite the ingested
infrastructure stack, additional ingestion infrastructure can be
included in the future.

Details of the data catalog are described in *D4_2 Public Listing
(Catalog) of FAIRiCUBE data resources* and open issues are listed in the
[public GitHub repository](https://github.com/FAIRiCUBE/catalog/issues).
These issues represent the project\'s active efforts to improve the
functionality, consistency, and usability of the FAIRiCUBE catalog,
which plays a central role in supporting FAIRiCUBE's mission to enable
findable, accessible, interoperable, and reusable data for spatial and
environmental analysis.

Most of the current discussion is about metadata enhancements. FAIRiCUBE
project members have suggested introducing new metadata fields to
connect catalog entries to their related validation and visualization
records as well as provenance information. This would render datasets
and analysis resources more traceable and, thus, allow users to more
easily assess their quality and fitness. Efforts are simultaneously
underway to sustain and enhance the controlled vocabularies (codelists)
employed across the catalog. These enhancements are required for the
provision of semantic interoperability and a harmonized classification
of resources.

The GitHub issues further reflect ongoing maintenance efforts to enhance
the usability and coherence of the catalog. Numerous issues identify the
necessity to rectify heritage data requests that are redundant or
obsolete, thereby enhancing the content of the catalog. Other
maintenance efforts entail systematic revision of metadata entries to
amend inconsistencies and develop consistent formatting, thereby
enhancing the credibility and navigability of the catalog.

Integration and tooling are also high up on the open issues. One of the
key foci lies in the customization of the interface of the STAC Browser,
which is utilized for exploring catalog entries. The changes suggested
are intended to align this interface more closely with the requirements
of the users of FAIRiCUBE and to enhance both its visual representation
and functional properties. Finally, a few issues reflect the need for
thorough documentation and easy-to-follow guidelines for contributors.
Effort is underway to develop accurate instructions for adding metadata
records, so additions are made according to FAIRiCUBE\'s requirements.
In the following the components of the FAIRiCUBE data catalog are
evaluated and described in detail.

### Dataset metadata

For each dataset used by the Use Cases, regardless of if this was
ingested from an external source, e.g., Copernicus or generated within
the project, a metadata record was created in the dataset metadata
catalog, simplifying reuse of data across use cases. While in most cases
the data was ingested to either the EOX or rasdaman infrastructure, in
some cases external APIs were accessed directly. In these cases, the
dataset metadata includes information on how to access this API, making
it easier for others wishing to reuse the same source in their work.

After comparison with other Geo Metadata Systems and their usage, e.g.
INSPIRE, ISO 19115, GeoDCAT, a set of metadata elements was specified as
follows:

-   General Information, e.g., Title, ID

-   Assets (links to related resources) , e.g., thumbnail, overview,
    data

-   Axis Information, e.g., CRS, bounds, UoM

-   Band Information, e.g., Definition, UoM

-   Accessibility Information, e.g., Access Control, APIs, Other formats

-   Relevant Dates, e.g., Creation, Provision

-   Validation, e.g., Quality Measures

-   Data Origin / Provenance, e.g., Data Source, Processing

-   Legal Information, e.g., License

Where possible, the dataset metadata was structured in accordance with
STAC Core or its Extensions. In the cases where no suitable element was
available, new elements were proposed to a fitting extension. Details of
these elements and their mapping to STAC are available from *D4_2 Public
Listing (Catalog) of FAIRiCUBE data resources*.

While STAC has amazing flexibility in its extension mechanism, this can
also become an issue due to the lack of governance, leading to new
overlapping extensions continuously emerging. As many extensions seem to
be triggered by projects contending with a short timeframe, many
worthwhile proposals don't gain necessary support, increasing the
confusion.

A [Catalog Editor](https://catalog-editor.eoxhub.fairicube.eu/) has been
implemented enabling users to create metadata records for new datasets.
In the case of data to be ingested on rasdaman, creating such a record
also served as a trigger for the ingestion of that dataset into the
rasdaman system by CU staff. In the case of data to be ingested on the
EOX platform, the user also had to ingest the data to AWS storage and
provide a link to the dataset when creating the metadata record.

### Resource and analysis metadata

The FAIRiCUBE analysis and processing (a/p) resources are the building
blocks that were created during the project lifetime to extract insights
from the data processed and/or analysed by the use cases. These
resources include algorithms, processing workflows, and analytical tools
tailored to specific use cases. The a/p metadata comply with the STAC
standard, specifically both the STAC core and the STAC-ML extension and
are published in the FAIRiCUBE Catalog.

Their structure is based on the requirements from the use cases and is
designed to be as comprehensive as possible, capturing key details such
as the resource's purpose, technical specifications, input and output
data and computational requirements. To support semantic consistency,
some metadata elements are managed through codelists maintained by the
project partners following an agreed procedure based on the use of
GitHub repository and GitHub form. A user-friendly web application is
available to help users create and update metadata files and validating
the entered data. In addition, the forms allow uploading files with
details of computational demands, particularly useful in terms of reuse,
to enable proper planning (users need to know in advance what kind of
infrastructure is required to run a resource effectively) and estimate
costs. For more details about the metadata, see Deliverable *D4.3:
Public Directory (Catalog) of FAIRiCUBE Processing/Analysis Resources*.
The metadata framework for FAIRiCUBE processing and analysis resources
is fully in place, and accessible from the Hub, offering a structured
and interoperable way to describe and share each resource:

-   [ML resource
    > catalog](https://catalog.eoxhub.fairicube.eu/collections/ML%20collection)

-   [non-ML resource
    > catalog](https://catalog.eoxhub.fairicube.eu/collections/no-ML%20collection)

-   [Resource Metadata Form](https://fairicube-md.epsilon-italia.it/)

Feedback from the use cases on the metadata structure and web form
usability is positive as well as on the use of GitHub repository for the
management of the codelists. The catalog effectiveness relies on users
providing complete and accurate metadata. Detailed descriptions are
essential to ensure the resources can be discovered, understood and
reused by others. Currently, most metadata files for the a/p resources
have yet to be provided by the various use cases. The metadata catalog
for analysis and processing resources is built using standardized
formats and clear descriptions, making it easy to reuse in other
contexts like the Green Deal Data Space (GDDS). Its structured and
consistent design allows other platforms to integrate and use the
information without needing major adjustments, supporting better data
sharing and collaboration across projects.

### STAC catalog and catalog browser

As outlined in the introduction to chapter 2.2, the initial intensions
of developments for a FAIRiCUBE catalog did not target a full-fledged
catalog concept covering all geospatial-related datasets with all their
eventualities. Such a development would have been far out of scope of
FAIRiCUBE and would require a multi-year project by its own, as has been
proven by the INSPIRE initiative. The FAIRiCUBE catalog should, however,
provide an easy-to-handle tool to ingest and offer metadata about used,
generated and offered datasets in FAIRiCUBE which are not available
elsewhere.

The initial decision to utilize modern STAC concept together with some
GitHub tools to achieve this goal turned out to be insufficient. The
selected GitHub tool isn\'t capable of handling amounts and/or type of
metadata fields required for the FAIRiCUBE catalog. STAC on the other
hand, initially developed by the satellite image community to provide a
fast and simple catalog for online handling of large quantities of
satellite images, turned out to currently not provide the structures
required to cover more complex scenarios based on broader datasets of
the geospatial domain. Nevertheless, FAIRiCUBE tried to define and
provide such a structure and will submit the respective enhancements and
extensions to the STAC community for adoption. All this resulted in
multiple intermediate but imperfect solutions and a highly undesired
delay of the delivery of the final catalog.

An interface for the FAIRiCUBE catalog the dynamic STAC-fastapi Web-GUI
has been chosen. For this interface a full-text search has been
requested by the Use Cases. However, such functionality is already in
progress by the STAC-fastapi developers and therefore only a minor
enhancement has been generated in FAIRiCUBE. Further, an extension of
the search functionality has been added as additional filters which
allow full-text search at selected meta data field level (being case
insensitive and using \"%\" as placeholder for any string). An
unspecific full-text search across all meta data fields could not be
implemented.

### Catalog editor

As the initially selected GitHub tool turned out to be insufficient to
handle all the required metadata fields a FAIRiCUBE specific catalog
metadata editor has been developed. This editor provides a Web-GUI with
integrated format, plausibility and validity checking. The editor
provides explanatory information for each field and allows to extend the
metadata set for various user requirements (e.g. vertical axis, time
axis, thumbnails, multiple assets, bands, etc.).

The Catalog Editor is a frontend to a GitHub repo. When a form is
submitted, a GitHub Pull Request is issued as a new branch, the STAC
JSON for the metadata record is created, and the user is automatically
set as watching, thus receiving notifications of updates depending on
their GitHub notifications configuration. When the data is ingested to
rasdaman, any progress, problems, or discussions are documented in
GitHub issues associated with the respective Pull Request, enabling
interested parties to follow the progress and provide additional
feedback or information as well as provide a history.

Utilizing the GitHub Pull Request approach allows us to easily integrate
governance into the dataset metadata creation process as we can utilize
the GitHub Reviewer mechanism as required. Once the Pull Request gets
merged, the STAC JSON metadata record is available on the GitHub repo
and accessed by the STAC FastAPI. At present, subsequent modification of
dataset metadata records can only be done manually by directly editing
the STAC JSON metadata record. More information on this process is
available from D5_2\_Deliverable_FAIRiCUBE-Ingestion-Pipelines.

## Datacube analytics in rasdaman workspace

This section documents progress in the rasdaman workspace, outlining the
initial plans, the features delivered, and how user feedback shaped the
implementation. Overall, there was a focus on improving usability, data
accessibility, performance, and integration with the wider data science
ecosystem.

### Ensuring Data Interoperability

Users reported that some of the OGC API supported by rasdaman do not
return compliant responses. Subsequently, we worked to improve
compliance, specifically in the WCS API, ensuring responses validate
against the official XML schemas. This was crucial for broader data
interoperability and compatibility with existing GIS and XML tools. We
achieved almost full compliance, with a single remaining issue due to a
standard that does not foresee support for temporal date/time
coordinates in the bounding boxes of coverages in a WCS GetCapabilities
response. The correct solution would be updating the standard and
corresponding XML schemas; however, this follows a slower
standardization process that cannot be completed before the project\'s
end. Nevertheless, we have not encountered *any* problems caused by this
in practice, with numerous clients and tools.

### Enhancing Irregular Temporal Axis Capabilities

During ingestion of datasets in FAIRiCUBE we encountered a limitation of
the WCS specification related to datacubes with an irregular temporal
axis. In particular, coordinates on an irregular axis are interpreted as
single points, e.g. a data slice at coordinate 2025 allows that data
slice to be accessible only at that exact point, i.e. it is not possible
to allow accessing it also at 2024. This semantics does not fit many of
the datasets, where a certain data slice is valid within a given
interval like 2015-2018, rather than a single point. To address this
shortcoming, we introduced the concept of [area of
validity](https://doc.rasdaman.org/05_geo-services-guide.html#areas-of-validity-on-irregular-axes),
which allows us to extend each irregular coordinate from a single point
to an area. The areas can be specified per coordinate individually, or
alternatively as the whole area from one coordinate to the next one on
the axis. This allowed us to import all datasets requested by users in
the project while correctly matching the temporal validity of data
slices with the original data when modelled as a datacube with a
temporal axis.

### Advanced Calendar Capabilities

The WCPS standard affords for relatively basic functionality when it
comes to querying temporal datacubes, allowing at most to specify fixed
date/time strings such as "2025-05-01T10:00:00". This is not sufficient
for even slightly more demanding queries, e.g. "do some analytics on
datacube X for March across all available years". To this end, we have
designed and implemented [advanced calendar
capabilities](https://doc.rasdaman.org/05_geo-services-guide.html#calendar-capabilities)
for addressing temporal coordinates in WCS / WCPS. This primarily
concerns sub setting on a temporal axis, but also other operations, e.g.
aggregating data over a time series per temporal unit such as day,
month, year, etc. This feature significantly expands the type of
timeseries analytics possible in rasdaman, and hence the usability of
the service for data science tasks.

### Simplified Geo-to-Grid Coordinate Translation

Feedback from UC3 identified the geo-to-grid coordinate translation
process within datacube sub setting as complex and unpredictable. This
is relevant for applications that may wish to perform the translation
themselves, on client side. We undertook a comprehensive review of the
existing translation logic, identified the sources of complexity, and
developed a new formula based on a more robust and well-defined
mathematical foundation
([documentation](https://doc.rasdaman.org/05_geo-services-guide.html#subsetting-behavior)).
Extensive testing was performed to ensure accuracy and consistency
across different datasets and coordinate systems.

### Python Code in User-Defined Functions

Originally rasdaman supported extending the server query functionality
with UDFs implemented in the C++ programming language. Feedback from UC2
indicated that C++ is not suitable, as the data science / machine
learning (ML) ecosystem is predominantly Python-oriented and caused
significant obstacles in integrating ML inference on datacubes in
rasdaman. To address this shortcoming, we developed support for
executing UDFs implemented in Python. In UC2 this resulted in a much
simpler and more robust solution for integrating ML inference with a
PyTorch model for crop segmentation on Sentinel-2 data directly into the
rasdaman WCPS service. As the generalization of the python UDF
development raised some conceptual issues, ML training and inference
were agreed as out-of-scope on rasdaman workspace. Further details on
the python UDF and the machine learning implications are described in
deliverable report *D3.3 Processing and ML applications*.

### OpenEO & OGC API Coverages Support

While initial support for
[openEO](https://doc.rasdaman.org/05_geo-services-guide.html#openeo) and
[OGC API
Coverages](https://doc.rasdaman.org/05_geo-services-guide.html#ogc-api-coverages-oapi)
was developed outside of FAIRiCUBE, we aimed to enhance these APIs
within FAIRiCUBE. Mainly we focused on integrating [openEO batch
jobs](https://doc.rasdaman.org/05_geo-services-guide.html#batch-jobs)
into the FAIRiCUBE infrastructure, providing a convenient way to
asynchronously execute complex data processing workflows. These API
expand access to the FAIRiCUBE datacubes through further clients, so
support for them is certainly valuable in FAIRiCUBE. On the other hand,
they are still relatively new specifications, not official standards,
and do not really offer any new capabilities of features over OGC WCS
and WCPS (except for openEO batch jobs which have no counterpart in
WCPS); in fact, the openEO implementation in rasdaman maps to WCPS
internally. User feedback has been positive, although there has been
confusion about the version of OGC API Coverages supported because it
has not been accepted as an official standard yet and the specification
is still in flux. The currently implemented openEO version in rasdaman
can therefore considered as outdated and is subject to further updates.

## Datacube analytics in EOX Workspace

This section documents progress in the EOX workspace, outlining the
features delivered, and how user feedback shaped the implementation.
Overall, there was a focus on processing and machine learning
capabilities, visualization as well as documentation and validation
efforts. Most of the applications and services deployed to the EOX
workspace are described in detail in the deliverable report
*D4_5\_FAIRiCUBE_Apps_supporting_community_collaboration*.

### Advanced processing capabilities

The EOX workspace has been enhanced with processing capacity to manage
the needs of long-running or processor-intensive operations. A
significant addition is the ability to run Jupyter Notebooks in
headless, non-interactive mode so that these sorts of operations can be
run independently from the live JupyterLab session. This functionality
is exposed via the use of pygeoapi, which serves as the service backend
to manage the asynchronous execution requests. Headless execution would
further allow to tab into additional processing and funding resources,
e.g. provided by the [ESA network of
resources](https://nor-discover.org/)[^5] (NoR). In theory, more
demanding and thereby more expensive compute tasks can be transferred to
a different AWS tenant and the billing routes to the NoR vouchers
credited at EOX instead of the NILU AWS tenant where a large amount of
FAIRiCUBE compute and storage costs budget has been allocated to. In
practice, however, the headless execution was only tested on small jobs
and gaining overview of consumed NoR resources proved to be very
difficult which limits the practical impact for the project. As the
foreseen infrastructure budget for the UC work activity was sufficient,
there was no push to operationalize the execution of headless jobs and
tapping the additional NoR funds.

To complement the improved processing capabilities, notebook execution
management is addressed using papermill, which provides structured
feedback regarding execution outcomes in order for users to monitor
outputs, log recordings, and debug errors without physically interacting
with the notebook. On top of this, the infrastructure has been extended
to accommodate the usage of GPUs, which is fundamental in accelerating
deep learning tasks as well as other parallel computation processes. A
specialized notebook viewer has also been included, allowing users to
display notebooks---code, output, and visualizations---without launching
the complete JupyterLab interface, making it easier to review output.

### Machine learning capabilities

One significant area of improvement in EOX workspace concerns the
incorporation of machine learning capabilities. The platform now
features a collection of tools that support the entire lifecycle of
machine learning model creation, from experimentation to deployment.
Behind this enhancement is the addition of the MLflow library, which
comprises several components that are responsible for performing various
functions. MLflow Tracking enables the tracking of parameters, metrics,
and artifacts during the training runs, thus increasing experiments\'
reproducibility and making comparative studies easier. MLflow Projects
helps with the packaging of machine learning code in portable and
reproducible constructs that can be executed in different environments.
With MLflow Models, users have the ability to save and share trained
models with a standard format that is ready for deployment in various
platforms. In addition, MLflow Model Registry is a central model store
enabling versioning, assessment, and management of models in
collaborative environments. In combination with MLflow, TensorBoard has
been incorporated to enable the visualization of training metrics in
real time, thereby providing users with insights into model performance
using interactive graphical representations. For dataset and experiment
management requirements, Data Version Control (DVC) has also been
leveraged. DVC aids in managing large data files and model artifacts
along with enabling users to define and execute reproducible pipelines
and track different experimental variations over time.

However, most of the machine learning capabilities have only been
verified but not used in production, i.e. as part of the ML workflow
while testing the right ML method and tuning the parametrization.
Usability, streamlining of ML related documentation and transparency
have been proven widely, but unfortunately not within FAIRiCUBE. This is
due the resource constrains and GPU availability for ML applications on
the EOX workspace. Only late, a GPU server option was made available to
use cases and the headless execution of larger jobs only passed the
testing phase. In addition, and in contrast to the original project
plan, most of the FAIRiCUBE use cases did not include large machine
learning applications which would require careful management and
documentation of results and parameters enabled by MLflow tools.

### Visualization

Visualization of results is another advance in functionality of the EOX
workspace. In order to address this requirement, various tools have been
integrated to allow users to create interactive dashboards and visualize
their process results. Apache Superset has been added as an
enterprise-grade business intelligence platform with the ability to
create sophisticated dashboards out of large datasets. It offers users a
feature-rich interface to query and visualize data in numerous formats.
Furthermore, the EO-Dashboard has been installed to act as a user-facing
interface for visualizing Earth Observation outcomes, allowing
researchers to contextualize environmental data within spatial and
temporal dimensions. EO-Dashboard and Apache superset have finally not
been chosen for visualization due to the higher technical entry level
for users to get started.

The open-source analytics and interactive visualization web application
Grafana is also included in the visualization ecosystem. It provides
real-time monitoring capabilities for metrics and infrastructure
performance. In addition, it is used to produce web-based dashboards,
charts and further insights into the use case work. The use cases lead
by partner Natural History Museum Vienna (NHM) have adopted Grafana
visualization e.g. for their Vienna City Fly citizen science project.

### Additional capabilities

While many tools have been incorporated directly into EOX workspace,
several external applications have been put in place to enhance the
platform but not be part of the core environment. A monitoring tool to
track cloud resource usage is one of these systems, particularly in
setups like AWS. This relies on Prometheus for metric gathering and
Grafana for visualization to allow users and administrators to see CPU,
memory, disk, and GPU usage over time. Another component is the
documentation portal (Digital Library), which is realized by a
Read-the-Docs instance (see chapter 2.6.1). This portal is used to host
and maintain the FAIRiCUBE project\'s technical documentation to
facilitate simplicity in comprehension and utilization of the processes,
tools, and data generated within the platform by the users.

One of the functionalities that fall outside of the active UI is manual
JupyterLab kernel creation capability for users. While such
functionality is available, it is disabled by default as it represents a
high risk of interfering with already running kernel environments. This
functionality may be enabled in the future under controlled conditions
or for advanced users with higher privileges. Finally, an external
metadata catalog has been provided to facilitate the discovery,
description, and reuse of datasets and workflows (see chapter 2.2).

## Data and code sharing

### GitHub

GitHub is a popular platform for code and data sharing in research,
software development, and data science and one of the most important
software infrastructure-[pillars for
FAIRiCUBE](https://github.com/FAIRiCUBE)[^6]. Its Git-based distributed
version control system enables collaborative development, version
tracking, and open contributions from various users. By hosting code
repositories on GitHub, FAIRiCUBE users can promote reproducibility,
enable community contributions, and enhance the efficiency of the
collaboration process. In addition, GitHub maintains the precepts of
open science by enabling public access to source code and data. Users
are given the flexibility to provide structured project documentation
through README files, complete usage instructions, and explanatory
examples. For large datasets, GitHub can be easily supported with
solutions like Git Large File Storage (LFS) or linked to remote data
repositories like Zenodo.

Furthermore, GitHub provides issue tracking, pull requests, and
continuous integration capabilities that improve the code quality and
project maintainability in significant ways. Especially GitHub issues
are widely used to improve FAIRiCUBE services in a structured,
transparent and efficient manner. By using GitHub for sharing data and
code, FAIRICUBE members not only maintain the integrity of their
deliverables but also participate in a larger ecosystem of reusable and
auditable knowledge.

### Zenodo

Zenodo is an open-access repository developed by CERN within the
European OpenAIRE initiative with the aim of supporting the long-term
preservation and sharing of research results. The site offers
[FAIRiCUBE](https://zenodo.org/communities/fairicube/records?q=&f=resource_type%3Adataset&l=list&p=1&s=10&sort=newest)[^7]
a stable means of sharing datasets, publications, software, and other
digital artifacts with the added assurance that all materials shared are
minted with a Digital Object Identifier (DOI) to enable proper citation
and long-term availability.

One of the primary strengths of Zenodo is its support for the FAIR data
principles---Findability, Accessibility, Interoperability, and
Reusability which is ideal especially for FAIRiCUBE. By allowing users
to upload files as large as 100 GB (due to a granted request), and by
accepting a wide range of metadata formats, Zenodo is perfectly
positioned for dataset sharing across all scientific disciplines. Its
integration with GitHub is especially handy, in that it provides
automatic archiving of software releases from public repositories with
DOI versioning for code.

Zenodo meets the European Commission's guidelines on reproducibility and
open data. Users can choose to make their access open or closed, specify
the licensing conditions, and associate their uploads with the related
research outputs, e.g., journal articles or conference proceedings. In
FAIRiCUBE, Zenodo is used to publish all [deliverable and milestone
reports](https://zenodo.org/communities/fairicube/records?q=&f=resource_type%3Apublication&l=list&p=1&s=10&sort=newest)[^8]
(including scheduled updates), [outreach and dissemination
material](https://zenodo.org/communities/fairicube/records?q=&f=resource_type%3Aposter&f=resource_type%3Apresentation&l=list&p=1&s=10&sort=newest)[^9]
(poster, presentations, etc.) and
[datasets](https://zenodo.org/communities/fairicube/records?q=&f=resource_type%3Adataset&l=list&p=1&s=10&sort=newest)[^10]
that have been created as part of the FAIRiCUBE use case work. While the
persistence storage and provision for documents is ideal for FAIRiCUBE,
the hosting of data does not allow for any sub-setting or
spatial-temporal query, i.e. entire data sets have to be downloaded
which was one of the key obstacles for FAIRiCUBE to overcome.

### EBV

The [EBV Data Portal](https://portal.geobon.org/datasets)[^11],
developed by the Group on Earth Observations Biodiversity Observation
Network (GEO BON), is a centralized platform for the dissemination and
visualization of Essential Biodiversity Variables (EBVs). EBVs are
standardized metrics that aim to capture key aspects of biodiversity to
facilitate consistent monitoring and reporting across different spatial
and temporal scales.

The portal offers access to a wide range of EBV datasets portraying
numerous ecological attributes, such as species abundances, ecosystem
structures, and genetic makeup. In order to facilitate interoperability
and compliance with the FAIR (Findable, Accessible, Interoperable,
Reusable) data management principles, the EBV Data Portal utilizes the
\"EBV Cube Standard.\" The metadata standard builds upon existing
specifications, including the Attribute Convention for Data Discovery
(ACDD), and borrows elements of the Ecological Metadata Language (EML),
thereby facilitating the discoverability and usability of the datasets.

Users can interact with the portal through a user-friendly web
interface, which accommodates the upload, browsing, and download of EBV
datasets. Programmatic access to the resources of the portal is also
offered through a RESTful API. The API accommodates automated data
fetching and the integration of EBV data into analysis workflows,
enabling smoother research processes.

By providing a strong foundation for the standardization and sharing of
biodiversity data, the EBV Data Portal plays a key role in advancing
international biodiversity monitoring. It enables scientists,
policymakers, and conservationists to obtain high-quality, standardized
data required for sound decision-making and effective conservation
planning. FAIRiCUBE has been in contact with EBV representatives,
exchanged ideas on meta data description, data catalog issues and
received detailed information on datasets publication using the EBVCube
format. At the time of writing this report, no FAIRiCUBE datasets have
been published on the EBV data portal, but it is considered as an
alternative to Zenodo. However, as the API functionality is currently
limited and the web-based download has little advantages over the Zenodo
hosting, only the proximity to other relevant data biodiversity data
would bring additional value.

## Knowledge base

Aligned with the project's goal of making multi-thematic datacubes and
machine learning (ML) more accessible, the Knowledge Base services (KB)
is meant as an integrated support platform that lowers technical
barriers and broadens usability for public authorities, domain experts,
and researchers across disciplines. The KB consists of the following
three integrated services:

-   Digital Library: Centralized access to FAIRiCUBE documentation,
    onboarding materials, machine learning resources and practical
    \"Tips & Tricks\" based on use case experiences. It enables users to
    explore and understand practical applications of EO and ML on
    datacubes.

-   Query Tool: An interactive interface that allows users to perform
    both simplified and custom metadata-driven searches over the
    project's resources. By enabling precise filtering based on
    standardized parameters and existing metadata values, the tool
    facilitates efficient resource discovery.

-   Chatbot: An intelligent support agent that assists users in
    navigating the KB, clarifying concepts and accessing relevant
    resources. It serves as an entry point for users with varying levels
    of technical expertise.

The FAIRiCUBE Knowledge Base (KB) is designed as a flexible and
interoperable support platform that extends beyond the immediate needs
of the project. its modular structure and its standardized,
well-documented approach enable easy integration and adaptation across
other initiatives and domains, making it a valuable asset for broader
applications beyond FAIRiCUBE. Sections 2.6.1 and 2.6.2 below provide
insights into what has been effective so far and highlight areas that
still require improvement.

### Digital library

The infrastructure is established and
[operational](https://fairicube.readthedocs.io)[^12] and clear
instructions on how to contribute to the Digital library content are
[available](https://fairicube.readthedocs.io/en/latest/user_guide/howto_readthedocs/)[^13].
Some challenges remain, particularly with structuring the content and
organizing menu items for easier navigation. Users have reported some
issues with scrolling through the menu on the left, which may hinder
visibility of the menu items at the bottom. To further enrich the
documentation, partners' contribution is essential.

### Query Tool

The query tool infrastructure is established and
[operational](https://fairicube-kb.epsilon-italia.it/)[^14] and allows
users to interactively search for processing resources in different
ways, according to their level of expertise and the desired level of
granularity. It is possible to carry out keyword searches,
[pre-configured
queries](https://fairicube-kb.epsilon-italia.it/query-tool-almade), at
and more [advanced custom
queries](https://fairicube-kb.epsilon-italia.it/query-tool-driven). For
each resource that meets the criteria, key properties are shown to
clarify its function and how it was used in the use case, along with a
link to the full details in the metadata Catalog. To further enrich the
search functionality, currently relying on metadata keywords, more
complex semantic search mechanisms can be designed and implemented.

### Chatbot

The Chatbot infrastructure is established and
[operational](https://fairicube-chatbot.epsilon-italia.it/)[^15] and can
in theory help users to find and navigate the Digital Library and the
GitHub repositories in a natural language correspondence. At the time of
writing, the chatbot is still in a very experimental stage and users
experience latency in responses. Due to challenges in engaging project
partners to actively contribute and deliver content and issues in the
LLM pipeline, the overall completeness and effectiveness of the
documentation query remain limited. The chatbot relies heavily on the
underlying documentation as its primary knowledge source and gaps
directly affect its ability to provide accurate and comprehensive
responses. Overall, the Chatbot remains a technical demonstrator but due
to performance, limited input for and pipeline issues, it does yet
provide added value, and its output has to be evaluated with extreme
care.

## Validation framework

![](media/image4.png){width="5.068810148731409in"
height="3.8467410323709537in"}The FAIRiCUBE validation framework brings
together quality checks from across all project work packages. Figure 3
shows how the different validation efforts are connected within the
different areas from data ingestion validation to validation of
communication and dissemination KPIs. The main items of the validation
framework are described in deliverable *D1.2 Validation report*.

The main areas of validation covered by the framework include:

-   **Overall validation coordination**: A central activity that
    provides an integrated view of all validation efforts across the
    FAIRiCUBE project, ensuring consistency and completeness.

-   **Use Case validation**: Focuses on checking whether each Use Case
    is well-defined, relevant, and meets its intended purpose. This
    includes reviewing Use Case specifications, user needs assessments,
    and whether the outputs are fit for purpose.

-   **Processing and machine learning validation**: Assesses the
    accuracy and robustness of data processing and ML pipelines. This
    includes validating algorithm implementation, documentation quality,
    benchmarking, and checking for potential biases or ethical concerns.

-   **Sharing functionality validation**: Ensures that the different
    components of the FAIRiCUBE Hub---such as data, tools, processing
    services, and visualisation---work correctly both on their own and
    together as an integrated system.

-   **Data ingestion validation**: Verifies that datasets entering the
    FAIRiCUBE platform are complete, consistent, and accurate. This
    includes checks on metadata, data quality, and comparisons with
    original sources using both statistical and spatial methods.

-   **Communication and dissemination validation**: Uses key performance
    indicators (KPIs) to track the reach and effectiveness of
    FAIRiCUBE\'s outreach activities, including events, newsletters,
    social media, and publications.

-   **AI ethics assessment**: Reviews how AI is applied in the Use Cases
    to ensure that it is used in a fair, transparent, and responsible
    manner, in line with ethical standards and user rights.

### Access, usability, and provisioning of validation records

Based on the different aspects of the validation framework (outlines in
the following subchapters) and the respective checklists that have been
created and published in several deliverables (summarized in *D1.2
Validation report*) online validation forms have been developed and
[made available](https://forms.gle/bWAovoGzvUBDyaFF6)[^16]. The forms
have been structured to allow for a partial or full validation
documentation covering either

-   a dedicated use case (UC)

-   a defined stage of the UC

-   an overview-style or detailed or response

-   tick box answers or possibility to link to other resources (concrete
    validation results, scripts, records, etc.).

Thereby the use case lead, contributors and users of the FAIRiCUBE Hub
services can either provide a very detailed intermediate or final
validation or choose to provide incremental updates. The level of detail
of the answers can also be adopted to the time efforts and availability
of contributors. After all, the validation framework is not supposed to
be mandatory but if a validation is foreseen and desired in the UC work,
we want to provide a standardized method and an easy access to the
providing the validation records.

For simplicity, we have chosen [Google
forms](https://workspace.google.com/products/forms/)[^17] as the
platform for creating, distributing the forms and collecting the
validation records. For saving of intermediate records before
submission, a Googe account may be required which is not in line with
our use access and management strategy (as described in chapter 2.8) but
this not a requirement. If the validation forms are to be improved, an
alternative standalone webservice is advised. Given the demonstrator
stage of the validation framework, setting up the online form and
maintaining it through Google forms was sufficient.

Making advantage of the flexible structure of the forms, each UC can
submit several validation records which are stored online and send as
statis backup to the submitter of the forms. Main challenge lies now in
the aggregation and provision of the validation records which is
currently a manual process. Each validation record can be exported as
columns (or table) data and used for external merging. Based on the
manual review of completion, a certification of the validation efforts
is envisioned.

So far, the use case feedback towards the online forms have been
positive and several validation records have been collected. Submission
of a full validation of a UC with only minimal details takes several
minutes but requires the knowledge of the deliverable reports as the
validation forms address all the validation aspects by single key words
only. In a next development step, "balloon tips" or expanding text
information will significantly improve the understanding of the keywords
and improve the answers. Additional efforts will also need to be
invested to streamline the aggregation, provisioning of the individual
records and issuing of a certification which can be used to demonstrate
the validation efforts by the use cases. This can be a starting point
for a more general validation of scientific work to support FAIR and
TRUSTable data science data and data science work.

### Validation of Use Cases

Validation of UCs in FAIRiCUBE focuses on assessing whether each case is
clearly defined, aligned with project goals, and practically applicable.
It involves checking the completeness and clarity of UC specifications,
evaluating whether the right data and methods are used, and conducting
user assessments to ensure the outputs meet real-world needs.
Fit-for-purpose checks are applied to confirm that the results are
suitable for the intended context. This process also includes
documenting findings and communicating them effectively to stakeholders.
Importantly, UC validation is closely connected to the validation of
processing workflows and platform functionality, ensuring consistency
across technical and thematic components.

### Processing and machine learning validation

Processing and machine learning validation in FAIRiCUBE ensures that
data workflows and algorithms used within the UCs are reliable,
well-documented, and ethically sound. This includes validating data
cleaning, transformation, and integration steps, as well as confirming
that algorithms are implemented correctly and perform as expected.
Benchmarking is used to compare performance across methods and datasets,
while thorough documentation supports transparency and reproducibility.
The validation process also pays attention to ethical considerations,
including identifying and addressing potential biases in machine
learning models.

### Sharing functionality validation

Sharing functionality validation in FAIRiCUBE ensures that the different
components of the Hub---covering information access, data availability,
processing tools, and visualisation---work smoothly both on their own
and as a unified system. This involves testing how well the various
parts integrate, whether users can access and share data and tools
reliably, and how intuitive and robust the interfaces are. The
validation also identifies any issues or areas for improvement and
checks that all shared resources meet project standards and user
expectations.

### Data ingestion validation

Data ingestion validation focuses on ensuring that datasets entering the
FAIRiCUBE system are accurate, complete, and consistent. This includes
checking for data integrity issues, validating formats, and comparing
both statistical and spatial characteristics of the ingested data with
original sources. The process helps confirm that data is reliable and
fit for use, while also documenting how it was validated. Any problems
identified---such as missing values, format mismatches, or
inconsistencies---are addressed to improve overall data quality and
maintain transparency throughout the project.

### Communication and dissemination validation

Communication and dissemination efforts are monitored through a set of
key performance indicators (KPIs). These KPIs---such as event
participation, website traffic, newsletter frequency, and social media
reach---serve as practical measures of outreach effectiveness. Progress
against these indicators is regularly reviewed and reported, helping to
assess how well FAIRiCUBE engages with its target audiences and
communicates project outcomes.

### AI ethics assessment

The AI ethics assessment in FAIRiCUBE ensures that artificial
intelligence is used responsibly and transparently across all Use Cases.
The assessment examines how AI models are developed, how transparent
their processes are, and whether they avoid bias or unfair outcomes. It
also provides practical guidance to ensure that AI is implemented
ethically throughout the project and reports on the validation results
in a structured and traceable way.

## User access and management

Access control and authentication of users are primary elements of
secure software development environments. As the FAIRiCUBE Hub services
are deployed at different existing software infrastructure with own user
access and management systems, developing a unified solution was
challenging and is to date only partially solved. As FAIRiCUBE heavily
depends on GitHub code sharing and collaboration and most FAIRiCUBE
members have a GitHub account, it was natural to extend GitHub
authentication to all FAIRiCUBE users. This way user access can be
granted through a single authentication method, user management still
controlled by the individual services, i.e. user roles and privileges
are defined heterogeneously.

GitHub uses the OAuth 2.0 protocol, which allows third-party
applications to obtain user data while protecting credentials. When a
user authorizes a third-party application, GitHub creates an access
token that includes specified scopes, which define the application\'s
permissions and restrictions (e.g., reading repositories, managing
issues, or accessing user profile data). Developers can control access
using GitHub Apps or OAuth Apps, with varying degrees of control and
integration. In practice, a GitHub account needs to be set up with
access to the FAIRiCUBE project. Then, the GitHub handle needs to be
communicated to the owner/responsible partner of the service. Table 1

# Use case specific feedback

## UC1

In this section, we provide comprehensive feedback on both the thematic
and technical aspects of UC1. UC1 aimed to address urban adaptation to
climate change at two distinct scales: the European Union level and the
local scale. To achieve this dual focus, the team implemented a common
underlying set of tools for data harmonisation and data cube analysis.
The work was structured around two distinct applications: the city
features collection data cube and species distribution models (SDMs) for
invasive plant species. Throughout the project, the team continuously
deepened their knowledge of cloud-based geospatial data analytics and
developed generic tools applicable across multiple contexts.

#### Achievements {#achievements .Sub-heading}

The implementation of UC1 yielded several notable successes. Data
harmonization and analysis pipelines were effectively developed,
heterogeneous dataset merged into harmonised data cubes, such as the
city features collection and the Luxembourg habitat data cube. The
clustering analysis of cities provided valuable insights into the
different vulnerability of cities to climate impacts. Data visualization
techniques were successfully employed to communicate complex findings to
both technical and non-technical stakeholders. The UC team also made use
of the FAIRiCUBE metadata registration services, ensuring compliance
with FAIR principles. Additionally, UC1 fostered productive synergies
with other use cases, creating a cross-pollination of ideas and
approaches that enhanced the overall project outcomes. Stakeholder
engagement was particularly strong, ensuring that the developed tools
addressed real-world needs. The use of geospatial data cubes in species
distribution modelling aligns with the latest advancements in the field
and contributed to their further development.

#### Challenges {#challenges .Sub-heading}

Despite these successes, UC1 encountered several challenges. The team
initially experienced hiccups in understanding and utilizing cloud
services (EOXHub, SentinelHub, Rasdaman), which caused delays in data
acquisition and processing. There was also a persistent challenge in
fully understanding the processing costs associated with cloud storage
and cloud-based analyses. The deployment of large-scale analysis and
machine learning models proved problematic, primarily due to a lack of
concrete applications or insufficient training data in some contexts.
The validation framework for the models and analyses could not be fully
developed during the project lifetime, making it difficult to quantify
the accuracy and reliability of some results.

#### Insights and Developments {#insights-and-developments .Sub-heading}

The team gained a deeper understanding of the cloud-based geospatial
processing landscape, including software, services, and data formats,
while also identifying current shortcomings and open questions in these
technologies. A significant achievement was the development of a data
cube processing and analysis toolkit, which offers potential
applications beyond the specific use cases addressed in this project.
The exploration of various visualization options led to innovative
approaches for communicating complex spatial and temporal patterns,
enhancing the accessibility of the findings for diverse stakeholders.

## UC2

The primary aim of UC2 is to develop standardized methods for better
understanding of the relationships between agricultural practices and
farmland bird biodiversity through the application of machine learning
techniques consistent over large scales. From a technological
perspective, the use case shows how a data cube-based data
infrastructure can facilitate improved access to biodiversity-related
information. This is particularly valuable for stakeholders with need to
analyse the interactions between biodiversity and human activities in
agricultural landscapes, in combination with regional environmental
variables such as land use, temperature, and precipitation.

#### Achievements {#achievements-1 .Sub-heading}

The primary achievement of use case 2 was the ability to confirm causal
relationship between the agricultural activity and biodiversity
indicator specifically on the case of crop rotation index and species
richness. The estimated effect suggests that higher crop rotation scores
are associated with increased biodiversity. Robustness of this
relationship was confirmed using a refutation analysis, which showed
negligible variation when the treatment variable was replaced with
random inputs, thereby supporting the validity of the findings.

Furthermore, a methodology for transforming raw bird species observation
data into scientifically meaningful estimates of biodiversity in
agricultural landscapes was established. This procedure involved the
development and application of ecological metrics, beginning with the
calculation of species abundance and species distribution, and
ultimately leading to the derivation of species richness as an
interpretable indicator of biodiversity. Importantly, species richness
was then employed as the key outcome variable in a causal analysis
framework aimed at quantifying the impact of agricultural activity,
particularly crop rotation. This approach enabled a consistent,
data-driven assessment of the link between farming practices and
biodiversity which supports demonstrating the critical role of
biodiversity indicators in ecological inference and decision-making.

#### Challenges {#challenges-1 .Sub-heading}

The development of UC2 encountered several methodological and technical
challenges. Initially, following the identification of key data sources,
it became clear that detailed farm activity data could not be used due
to privacy constraints and non-compliance with the FAIR data principles.
As a result, the analysis had to rely on the best available open-access
and freely distributed datasets. An important technical limitation
emerged from the incompatibility of source vector data formats with the
n-dimensional coverage model employed by data cube infrastructures which
was mainly a case of species abundance data. Moreover, the nature and
structure of several datasets made it more appropriate to perform
analytical processing prior to ingestion into the data cubes, rather
than within the cube environment itself.

Additional complexity arose from the data access mechanisms of several
sources, which involved complicated and non-standardized protocols.
These were not directly compatible with the automated ingestion
processes and thus required preliminary data acquisition and
preprocessing workflows. Furthermore, the use case was characterized by
a relatively limited integration of Earth Observation (EO) and
geospatial raster data. An exception was the use of the Normalized
Difference Vegetation Index (NDVI) derived from satellite imagery. While
raw NDVI data and basic calculations were readily accessible, more
advanced EO workflows such as the generation of multi-seasonal,
cloud-free mosaics were not available as standardized procedures and had
to be developed independently. These constraints together resulted in a
significant allocation of time and resources to data preparation and
pre-ingestion analysis. Consequently, this reduced the time available
for in-depth causal modelling using the ingested data within the data
cube environment.

#### Insights and developments {#insights-and-developments-1 .Sub-heading}

From a technological aspect, this study gave us a valuable insight in
the important principles of underlying data cube architectures,
particularly in the context of integrating and analysing
multidimensional environmental datasets within unified platforms.
Through practical engagement with data cube implementations, we got
insights of this approach in terms of data interoperability,
accessibility, and computational efficiency for large-scale
spatiotemporal analyses. Moreover, the use case enabled a comparative
assessment of two distinct technological providers as Rasdaman and EOX.
This comparison provided insights into the respective strengths and
limitations of their infrastructures, including differences in data
ingestion pipelines, query performance, user accessibility, and
integration capabilities with analytical tools. Such information is
important for informing the selection of appropriate technological
solutions for stakeholders aiming to utilize data cube frameworks in
biodiversity and agricultural monitoring applications.

## UC3

The focus of UC3 was on uncovering how *Drosophila* populations adapt to
their environments. We therefore conducted genotype--environment
association studies both at a continental European scale and at the
urban level within and around the city of Vienna. To support this, we
developed a workflow that included processing of genome-scale allele
frequency data and environmental data analysis that integrates datasets
from different sources. Our main goal was associating allele frequencies
with environmental variables and modelling the spatial distribution of
adaptive genetic variants. Over the course of the project, we built a
comprehensive and well-documented bioinformatic workflow, designed to be
adaptable to other environmental data.

#### Achievements {#achievements-2 .Sub-heading}

Key components of the bioinformatics workflow were implemented
successfully and data access to Earth observation data via APIs
functioned as intended. A dataset on pesticide usage in Europe was
successfully ingested into the Rasdaman services and is now available
for our analyses. UC3 developed a framework written in Python to
download Environmental data offered by the FAIRiCUBE infrastructure for
point coordinates only as single grid cell values, bypassing the
download of extensive amounts of data. This service is now also
available as Web Application hosted by NILU
([QueryCube](https://querycube.nilu.no/)).

One key achievement of the project was the successful application of
machine learning techniques to impute missing genomic data at the allele
frequency level. This approach enabled us to fill gaps in incomplete
population-level datasets with high accuracy, improving both the
resolution and reliability for downstream analyses. By using test
datasets based on real genomic variation, we were able to show that
machine learning models were able to correctly predict allele
frequencies for SNP positions with missing data. This approach reduced
data sparsity and carries potential to enhance genotype--environment
associations across spatial and temporal gradients.

We further made substantial progress in establishing and executing
analysis workflows on the EOXHub platform, this includes implementing
basic bioinformatic workflows and testing and executing custom scripts.
By "rescaling" the Use Case analysis from continent-wide genomic
*Drosophila* data to an urban-scale datasets, we acquired an in-depth
understanding of how local environmental variation influences
genotype--environment associations and how populations are structured at
different geographic scales. These analyses further allowed us to
compare genetic variation in rural areas and regions with pronounced
anthropogenic influences. In parallel, we gained valuable experience in
the design and implementation of citizen science initiatives. Through
direct engagement with the public, we learned effective strategies for
communicating complex scientific goals in accessible ways, tailoring
outreach methods to diverse audiences, and building enthusiasm around
data collection.

#### Challenges {#challenges-2 .Sub-heading}

Difficulties arose during the ingestion of genomic data into the data
cube format within the rasdaman platform. This process presented
technical challenges, primarily due to incompatibilities between the
structure of genomic datasets and the current ingestion mechanisms
supported by rasdaman.

## UC4

UC4 addresses the pressing need to evaluate and map the potential for
energy retrofitting and circularity in residential buildings to align
with the European Union's ambitious climate goals. Currently, buildings
are major contributors to both energy demand and greenhouse gas
emissions. More sustainable practices in construction hold promise for
reducing environmental impact, enhancing resilience, and averting raw
material price hikes.  However, a significant challenge lies in the
scarcity and fragmentation of data on building materials and properties.
This gap impedes informed decision-making on investments and the
promotion of circular and local materials.  Ultimately, the UC4 aims to
contribute to better energy policy, inform retrofitting strategies, and
support sustainable urban development efforts at the city scale. The use
case 4 work aims to answer the following research questions:

-   **RQ1:** Which input features (e.g., building geometry, construction
    > year, and residential type) have the most significant impact on
    > the accuracy of energy performance estimates for existing building
    > stocks?

-   **RQ2:** How do the predictive performances of the rule-based and ML
    > models compare in terms of key metrics such as RMSE and R², and
    > what are the underlying factors that drive any observed
    > differences?

-   **RQ3:** What implications do the findings have for designing
    > effective policies and investment strategies aimed at retrofitting
    > buildings to achieve energy efficiency and reduce GHG emissions at
    > a city scale?

#### Achievements {#achievements-3 .Sub-heading}

The UC5 work compared a rule-based heuristic model (EPISCOPE) and a
machine learning model (XGBoost) to estimate residential building energy
demand in several European cities (Oslo, NO; Barcelona, ES; Rennes FR).
Addressing RQ1, the results highlight heating days (HD), wall exposure
ratios, and building footprint ratios as the most critical input
features influencing estimation accuracy. These parameters significantly
improved the predictive performance of the rule-based model,
particularly in colder climates like Oslo and Rennes.

For RQ2, the heuristic model demonstrated moderate accuracy (R²:
0.08--0.63, RMSE: 54.92--81.89 kWh/m²), performing reasonably well in
Oslo and Rennes but struggling in Barcelona, where predictions had
little correlation with actual values. The XGBoost model underperformed,
particularly in Oslo (R²: 0.33, RMSE: 108.87 kWh/m²), likely due to data
scarcity and complexity. These findings indicate that while XGBoost
offers scalability, its predictive performance is highly dependent on
large, high-quality datasets and proper feature engineering,
highlighting the need for further exploration of alternative ML
approaches.

Regarding RQ3, the findings emphasize the need for data-driven
optimization in energy policy and retrofitting strategies. The
literature review highlights the increasing use of machine learning,
sensor networks, and geospatial data integration to enhance urban energy
modelling. However, challenges related to data standardization,
validation frameworks, and regulatory constraints remain, limiting the
scalability of energy modelling approaches. Future efforts should focus
on integrating higher-resolution building models (LOD2/LOD3),
sensor-based validation, and hybrid ML-rule-based techniques to improve
estimation accuracy. Addressing these gaps is essential for developing
reliable, scalable, and actionable energy demand estimation tools,
ultimately supporting effective retrofitting strategies, lower GHG
emissions, and smarter urban planning

#### Challenges  {#challenges-3 .Sub-heading}

One of the most significant challenges of the use case 4 execution was
due to the inaccessibility and availability of detailed household energy
consumption data serving as ground truth data. This kind of information
is typically regarded as sensitive or commercially confidential,
especially in relation to individual consumption levels. Therefore,
energy consumption data is not necessarily obtainable from official
sources like power utilities or infrastructure owners, limiting the
extent of detailed validation across cities.

In addition, data availability and accessibility differed greatly with
the city chosen, the initial source of data, the related restrictions on
use, and the particular nature of data gathered. These variations
required adaptation in choosing demonstrator cities. The original
intention to focus on Oslo, Vienna, Luxembourg, and Barcelona was
altered by data constraints, so Halle an der Saale, Oslo, Barcelona, and
Rennes were included instead.

A second major challenge was the inconsistency across cities in the
reporting and interpretation of energy consumption. The unit of
measure---whether consumption is expressed per building, per apartment
unit, or in aggregate---and the prevailing determinants of energy demand
(e.g., cooling versus heating) differed markedly. This heterogeneity
made both the validation of predictive models and cross-city
generalizability of findings more difficult. It was also difficult to
calibrate appropriate parameter settings for the EPISCOPE[^30] modelling
tool. Basic parameters such as heating degree days, heated living area,
and building geometry (e.g., exposure ratios of walls) had to be adapted
to city-specific levels to comply with local reporting standards and
building types. These caused variable success in the validation of the
models: Oslo yielded satisfactory validation; Barcelona unsatisfactory
results; and Rennes only partial success in validation. Consequently, a
general overall assessment of the complete workflow is still awaited.

Machine learning comparative work relied on actual reported energy
consumption data where available. However, the inconsistencies in the
above data limited the extent and potential strength of such
comparisons. The lack of consistent high-quality input data directly
impacted the potential to extract consistent findings from the machine
learning outcomes across the different urban environments. Finally, the
constraints of current EU-wide classification frameworks, i.e., the
TABULA typology, were revealed through the project. Although useful as a
general indicator, the classifications do not reflect the degree of
granularity and heterogeneity of local building stock attributes and
energy lifestyles. Consequently, their usefulness for application in
high-resolution modelling and validation exercises is constrained,
especially where localized calibration is precluded by the availability
of incomplete or inconsistent data.

#### Insights and developments {#insights-and-developments-2 .Sub-heading}

All in all, the UC4 task team gained a deeper understanding to which
extend urban energy consumption data can be retrieved, predicted through
adopted building classification and who this concept can be generalized
across European cities. In principle, the classification serves as a
good foundation but due to its simplicity, the made assumptions and the
coarse division according to building age, construction materials and
usage, the accuracy of prediction is varying and might not produce
acceptable accuracy for all considered cities. The selected machine
learning approach was not able to overcome the issue as it is mostly due
to the inconsistency of reported data and data completeness.
Nevertheless, the method works efficiently, and given availability of
the input data, scales very well which make the upscaling straight
forward. When including the nature of the produced power, further
insights into greenhouse gas emission can be made on building levels and
energy efficiency renovations can incorporate savings of CO2 equivalence
which can be reported in addition to monetary benefits.

## UC5

In this section, we present an overview of the objectives and
methodology developed for UC5, which focuses on implementing the
European habitat classification system and vegetation mapping through
the integration of species occurrence records, environmental data, and
machine learning techniques. The primary aim of UC5 was to refine the
European Nature Information System (EUNIS) habitat maps by incorporating
real-world plant distribution data from museum collections and citizen
science sources, alongside topographic and climatic Earth Observation
(EO) data. Through this approach, the use case addresses critical gaps
in current habitat mapping practices, while also emphasizing the value
of biodiversity databases like GBIF and JACQ, and the potential of
ensemble modelling to predict vegetation patterns across Europe.

#### Achievements {#achievements-4 .Sub-heading}

UC5 developed R scripts with a machine learning-based approach for
characterizing and predicting plant community distributions, which is
still not largely exploited in Habitat classification together with real
occurrence data (e.g., GBIF). Building on the EUNIS classification, the
UC5 focused on selected habitats combining occurrence data at European
scale with EO environmental predictors, producing Occurrence Data Cubes.
The results will be made available to stakeholders and a wide audience,
together with the scripts created, ensuring reproducibility through
FAIR-compliant pipelines.

#### Challenges {#challenges-4 .Sub-heading}

Throughout its development, UC5 encountered a range of significant
challenges. A primary difficulty was the variability and quality of
species occurrence data retrieved from GBIF, particularly records
sourced from citizen science platforms like iNaturalist and Pl@ntNet,
where validation by experts was often limited or missing. Many records
fell outside expected native ranges, requiring meticulous filtering
based on official floristic resources like EuroPlusMed and FloraVeg.
Even after careful cleaning --- including excluding certain categories
of specimens, handling duplicates, standardizing coordinate systems, and
filtering observations with high location uncertainty --- some issues
remained unavoidable, highlighting the inherent limitations of
heterogeneous open-access data. Another major challenge was the need to
generate reliable pseudo-absence data, given the absence of confirmed
negative records in GBIF, which introduced potential uncertainties
despite methodological safeguard. Additionally, harmonizing multiple
data types (occurrence points, environmental raster data) into a
standardized grid format, while ensuring geographic and ecological
relevance, was possible but nonetheless complex and resource-intensive.

#### Insights and developments {#insights-and-developments-3 .Sub-heading}

The UC5 work provided several important insights into the use of machine
learning and real-world occurrence data for habitat classification.
First, it confirmed that combining species occurrence records with
environmental predictors positively affect the ability to predict the
distribution of plant communities, an approach largely absent in
traditional systems like EUNIS. The implementation of an ensemble
modelling strategy not only improved predictive accuracy but also
revealed key environmental drivers behind species distributions.

Moreover, the study emphasized the critical need for thorough data
cleaning and validation when using large heterogeneous datasets from
sources like GBIF, particularly to mitigate errors introduced by citizen
science and unverified records. Additionally, the scalable, reproducible
data workflows developed under UC5 established a workflow guide for
applying similar methodologies to other habitats or regions.

Finally, the initial comparison between predicted habitat distributions
and EUNIS official maps suggested strong potential for improving current
habitat classifications by integrating species presence and
environmental data, moving towards a more dynamic, data-driven view of
biodiversity patterns across Europe.

# Summary

This deliverable report gives an overview of the technical achievements
and results concerning the FAIRiCUBE Hub and its services. It assesses
the ability of the platform regarding data ingestion, processing,
analytics, and sharing, and its role in facilitating FAIR-compliant data
management and use case deployment. The report offers detailed feedback
on the components of the Hub, such as the catalog system, datacube
analytics workspaces (rasdaman and EOX), and knowledge base services. It
discusses the success in the management of metadata, cloud-based
geospatial computation, and machine learning functionality but also
states problems like interoperability of data, ingestion limitations,
and validation. FAIRiCUBE\'s alignment with the Green Deal Data Space
(GDDS) is also discussed, highlighting its feasibility for extended use
in environmental and scientific communities.

The report further presents use case-specific results, outlining the
success and problems faced within diverse research applications,
including urban climate adaptation, biodiversity analysis on farm data,
genetic-environmental correlations, energy-efficient building mapping,
and habitat classification. These use cases utilized FAIRiCUBE Hub
services to tackle large-scale spatial data but were confronted with
data availability problems, inconsistency in standardization, and
technical constraints in the implementation of machine learning
algorithms. Lessons are drawn from such experiences to further enhance
the development of FAIRiCUBE and inform future improvement in usability,
performance, and integration with external data sources. The deliverable
report can be seen an as comprehensive statement of FAIRiCUBE\'s
preparedness for wider use and commercialization and how it can be
improved further.
